# Source-by-source extraction guide

Research date: **2026-10-03**. This is the consolidated plan for all **21 named sources or source categories** in the six-page rare-disease atlas brief, including RARe-SOURCE from its introduction. The [PDF review](pdf-review.md) records page-level coverage and the original links. Each source below has its own acquisition workflow, identifiers/fields, graph mapping, access/reuse limitations and maintenance considerations.

## Recommended approach

Use **bulk ontology/data files** for MONDO, HPO and broad structured datasets; **documented APIs** for focused literature, variant, trial and grant queries; **approved exports or curated public pages** for organizations and assets. Retain native records and cited assertions before resolving them into a graph. An identifier match is not evidence of a shared disease mechanism, and a public web page is not necessarily a reusable bulk dataset.

The most material findings are:

- **Orphanet has two different access paths:** open scientific products cover disease/gene/phenotype data, while expert-resource data such as organizations and registries have request/contract conditions. Do not apply the scientific-product license to the whole site.
- **OMIM, NORD and Global Genes need source-specific access/rights decisions.** The guide identifies the access/export route and records what remains unverified; it does not claim permission was obtained. In particular, NORD's CSV request is for a disease-database subset, not a confirmed organization export.
- **RareConnect is archival**, following retirement on 5 December 2023. It is not a source of current messaging or fresh community activity.
- **PMC's old OA Web Service is retired.** Plan around current OAI-PMH/approved PMC Cloud distribution and item-specific rights rather than old download recipes.
- **Genetic Alliance in the PDF means the US organization.** Its embedded link settles the identity. Genetic Alliance UK is a distinct related source for Rare Disease UK's community network.

These findings are supported in the corresponding source sections below. Access failures are observations from this research environment, not proof that a source is globally unavailable.

## Evidence status and reproducibility

**Live-probed** means a bounded read-only sample or file header succeeded; it does not prove whole-dataset completeness, production throughput, pagination exhaustion or redistribution permission. **Documentation-reviewed** means official provider material was inspected but the proposed data route was not executed. **Proposed** labels graph design and recommended refresh schedules. **Conditional/unresolved** marks access, rights or interface details that must be settled before implementing that connector.

Compact evidence logs: [biology/release/API probes](research/biology-probes.json), [literature/trial/grant probes](research/literature-probes.json), and [MGI/UniProt probes](research/asset-probes.json). Community-page and terms observations are recorded inline. No full corpus harvest, account registration, access request, payment, outreach or production graph ingestion was performed as part of this research.

This file is assembled from reviewed notes under `docs/research/` and the [source catalog](../data/source/catalog.json). Rebuild with `python3 scripts/build_source_guide.py`; check inventory/link coverage and freshness with `python3 scripts/build_source_guide.py --check`. That check verifies document structure and inventory alignment, not biological correctness or endpoint behavior.

## S01 — OMIM

PDF pages: 3, 5. **Acquisition summary:** Registered/licensed bulk or API; current API details unverified

**Identity and official entry points.** OMIM is the Johns Hopkins University curated catalog of human genes and genetic phenotypes/disorders ([OMIM](https://omim.org/); [OMIM API help](https://omim.org/help/api); [Hamosh et al., OMIM.org](https://academic.oup.com/nar/article/47/D1/D1038/5184722)). OMIM's pages could not be fetched by the research browser, so the API help URL is supplied for follow-up but its current route details were not independently verified.

**What to extract and KG shape (proposed).** Focus on stable MIM entry identifiers, titles and alternate titles, entry type (gene vs phenotype), gene-to-phenotype/Morbid Map associations, inheritance labels, and cross-references. Model `OMIM phenotype --associated_with / mapped_to--> OMIM gene` with source/provenance, map key/relationship type, and inheritance attributes where present. Link gene nodes to NCBI Gene/HGNC identifiers using OMIM's `mim2gene.txt`; link phenotype entries through MONDO, Orphanet, and HPO only via explicit xrefs or reviewed mappings. Retain MIM numbers and entry types as separate identity dimensions; OMIM gene MIMs and phenotype MIMs are both numeric identifiers.

**Bulk/API routes and sample.** Start from [OMIM Downloads](https://omim.org/downloads). The provider-authored [OMIM service paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC4383985/) describes `mim2gene.txt`, `genemap2.txt`, the gene-map key and native-text downloads; after approval, obtain the current file list and schema from the supplied access instructions. Parse gene-map rows into individual phenotype associations while retaining phenotype mapping keys, inheritance and original row text. Do not use download credentials published in third-party code. The later OMIM.org article reports that `mim2gene.txt` is downloadable without registration; gene map and entry title/number files are on a secure HTTPS server after registration. It reports single-user academic, nonprofit, and government access by registration using institutional email; commercial redisplay/software incorporation requires a license. This is documentation-only evidence from the source's cited article, not a live download check. The OMIM API is documented at `https://omim.org/help/api`, but the official page was inaccessible to the web reader and no exact route or request was verified; do not build against guessed parameters. API access/key requirements should be confirmed from current OMIM help/access terms before implementation.

**Reuse, updates and pagination.** The NCBI-hosted OMIM legal statement says personal, educational, scholarly, and research use is allowed, while commercial use or redistribution requires a license from Johns Hopkins University ([NCBI Handbook, OMIM legal statement](https://www.ncbi.nlm.nih.gov/sites/books/NBK21101/)). This restriction makes OMIM unsuitable as an unreviewed redistributable bulk payload. Keep OMIM-derived text/records outside publicly redistributed graph releases unless the applicable license permits the exact use. Update cadence, API pagination and incremental-change mechanisms were not established from accessible official documentation; store retrieval date/version and plan periodic licensed refreshes.

**Pitfalls and feasibility.** Moderate feasibility for an academic KG once registered; low for a redistributable or commercial full-text/Morbid Map integration without a license. Prefer minimal identifiers and cross-reference assertions with license review over copied narrative summaries. OMIM annotations represent curated assertions and phenotype entries can be genetically heterogeneous; preserve the exact OMIM entry and relationship/source rather than collapsing to a single disease node. The OMIM article also describes Morbid Map as gene–phenotype relationships, not a simple equivalence map.

## S02 — ClinVar

PDF pages: 3, 5. **Acquisition summary:** Bulk XML/TSV; focused E-utilities; documentation-reviewed

**Identity and official entry points.** ClinVar is NCBI's public archive of submitted clinical variant interpretations, evidence, and their aggregations ([ClinVar](https://www.ncbi.nlm.nih.gov/clinvar/); [access/maintenance and use](https://www.ncbi.nlm.nih.gov/clinvar/docs/maintenance_use/); [FTP primer](https://www.ncbi.nlm.nih.gov/clinvar/docs/ftp_primer/)). ClinVar aggregates submitted assertions (SCV) into variant-condition RCV records and variant-level VCV records.

**What to extract and KG shape (proposed).** Extract VCV variation identity and alleles, RCV variant-condition pairings, SCV submissions/assertions and submitter context, clinical significance and review status, conditions and their database identifiers, genes, HGVS expressions, assembly-specific coordinates, and references/evidence where needed. Suggested edges: `Variant/Allele --in_gene--> Gene`, `Variant --asserted_for_condition--> Disease`, `SCV --supports_classification_of--> VCV/RCV`, and `ClinVar assertion --has_evidence/reference--> Evidence/Publication`. Keep source accession, version, submitter, review status, condition, and genome assembly on assertions. Use ClinVar Variation ID / VCV / RCV / SCV as distinct identifiers; an RCV is a variant-condition aggregation, and multiple RCVs may refer to one Variation ID.

**Bulk/API routes and sample (documented, not live-probed).** For full ingestion, NCBI documents the complete public XML files under `https://ftp.ncbi.nlm.nih.gov/pub/clinvar/xml/`, with weekly current XML and a retained monthly release; its summary table describes comprehensive XML as weekly and monthly archival. TSV summaries under `https://ftp.ncbi.nlm.nih.gov/pub/clinvar/tab_delimited/` are comprehensive and monthly; gene-condition source data are available at `https://ftp.ncbi.nlm.nih.gov/pub/clinvar/` and updated daily. VCF directories `vcf_GRCh37` and `vcf_GRCh38` cover only simple, precisely mapped short variants, so XML is safer for full KG coverage. For a focused API fetch, documented examples include:

```text
https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi?db=clinvar&term=FGFR3%5Bgene%5D&retmax=500
https://eutils.ncbi.nlm.nih.gov/entrez/eutils/efetch.fcgi?db=clinvar&rettype=vcv&id=VCV000014206
```

These exact forms are shown in the ClinVar API documentation, but were not live-probed here. Supported Entrez functions listed by ClinVar are `esearch`, `esummary`, `elink`, and `efetch`; use `retstart`/`retmax` and E-utilities guidance for paging large result sets, or FTP for whole-corpus ingestion. The FAQ states there is no dedicated batch-query interface.

**Reuse, updates and pagination.** ClinVar records are public and downloadable, but NCBI notes that some materials in NCBI resources may be contributed or licensed and require following rights-holder terms ([NCBI policies](https://www.ncbi.nlm.nih.gov/home/about/policies/)). Preserve submitter attributions and citation/evidence provenance; avoid assuming that all linked evidence text is public domain. Align refreshes with documented FTP weekly/monthly/daily schedules and use release snapshots/diffs or accession versions for reproducibility. E-utilities are suitable for selective lookups, not bulk record-by-record polling.

**Pitfalls and feasibility.** High feasibility for an academic or public KG via bulk XML/TSV. Variant IDs, allele IDs, VCV, RCV, and SCV have different scopes; do not conflate them. VCF is partial and coordinates differ: XML/tabular locations follow HGVS-style right shifting while VCF is left normalized. Variant-condition relationships may be multi-condition, multi-gene, or haplotype/genotype; preserve sets and assemblies rather than forcing every record into one SNV–gene–disease triple. Clinical significance can differ across submitters and review levels; retain assertions and conflict rather than flattening to a single truth value.

## S03 — HPO

PDF pages: 3, 5. **Acquisition summary:** Pinned ontology and annotation files; headers live-probed

**Identity and official entry points.** HPO supplies standardized human phenotype terms and disease annotations ([HPO project](https://hpo.jax.org/); [HPO ontology/annotation documentation](https://obophenotype.github.io/human-phenotype-ontology/); [downloads](https://github.com/obophenotype/human-phenotype-ontology/releases)).

**What to extract and KG shape (proposed).** Extract ontology terms, labels/synonyms, definitions, obsolete status, parent relations, and disease–phenotype annotations with qualifiers, evidence, references, onset, frequency, sex, modifiers, aspect, and biocuration. Model `Disease --has_phenotype--> HPO term` as an attributed annotation edge; keep negative (`NOT`) assertions as explicit qualified edges, never as omitted positives. Ontology edges are subclass relationships. HPO terms use `HP:nnnnnnn`; disease annotation identifiers include external CURIEs such as `OMIM:n`, `ORPHA:n`, and DECIPHER identifiers; gene files include NCBI Gene IDs and symbols.

**Bulk/API routes and sample (live-probed, small range).** The latest official GitHub release at check time was `v2026-09-01` (published 2026-09-03). It contains `hp-base.obo` (11.4 MB), `hp-base.owl` (48.3 MB), `phenotype.hpoa` (35.8 MB), `genes_to_disease.txt` (1.49 MB), and `genes_to_phenotype.txt` (20.8 MB). Pinned assets include [phenotype.hpoa](https://github.com/obophenotype/human-phenotype-ontology/releases/download/v2026-09-01/phenotype.hpoa), [hp-base.obo](https://github.com/obophenotype/human-phenotype-ontology/releases/download/v2026-09-01/hp-base.obo), and [genes_to_phenotype.txt](https://github.com/obophenotype/human-phenotype-ontology/releases/download/v2026-09-01/genes_to_phenotype.txt); PURLs `http://purl.obolibrary.org/obo/hp.obo` and `.../hp.owl` remain convenient moving targets. I sent a `Range: bytes=0-2047` request to the pinned phenotype annotation file: HTTP 206 returned only 2,048 of 35,816,037 bytes and confirmed a lowercase TSV header: `database_id`, `disease_name`, `qualifier`, `hpo_id`, `reference`, `evidence`, `onset`, `frequency`, `sex`, `modifier`, `aspect`, `biocuration`. Metadata comments use lowercase `#version` and `#hpo-version`. A similar range probe confirmed the summary gene file header: `ncbi_gene_id`, `gene_symbol`, `hpo_id`, `hpo_name`, `frequency`, `disease_id`. No general REST API is needed for full extraction. Pin the release tag instead of using a floating latest URL. Summary gene/phenotype files are derived conveniences and may lose annotation nuance; use `phenotype.hpoa` as the disease-annotation source.

**Reuse, updates and pagination.** HPO's published license page allows download/use subject to attribution, public version/date display, preserving file content and embedded logical relations, and acknowledgment in services/products ([HPO license](https://human-phenotype-ontology.github.io/license.html)). It does not present a blanket CC-BY license; keep the stated conditions. Releases are versioned and appear periodically; pin release tags and refresh on new release rather than paging an API. Release metadata and small annotation-file byte ranges were fetched; full assets were not downloaded.

**Pitfalls and feasibility.** High feasibility for a research KG with attribution/version metadata. Annotation records include positive and negative phenotypes, evidence and frequency; preserving rows avoids loss when summaries collapse multiple references or contradictory frequency evidence. An HPO phenotype assertion attached to a disease entry is not automatically a direct gene–phenotype assertion. `genes_to_phenotype` and `phenotype_to_genes` are derived; the latter propagates to ontology ancestors, so avoid treating its rows as direct curation. Ontology terms can be obsolete/replaced and the ontology has several subontologies (phenotypic abnormality, inheritance, onset/clinical course, modifiers); don't treat every term as a symptom.

## S04 — PubMed

PDF pages: 3, 5. **Acquisition summary:** E-utilities or baseline + updates; small API samples verified

**Official URLs:** [PubMed](https://pubmed.ncbi.nlm.nih.gov/), [Download PubMed Data](https://pubmed.ncbi.nlm.nih.gov/download/), [E-utilities help](https://www.ncbi.nlm.nih.gov/books/NBK25501/), [E-utilities in depth](https://www.ncbi.nlm.nih.gov/books/NBK25499/), [PubMed XML DTD](https://dtd.nlm.nih.gov/ncbi/pubmed/out/pubmed_250101.dtd).

**Route (doc-only):** For targeted/initial discovery, ESearch at `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi?db=pubmed&term=...&usehistory=y` with `tool` and `email`; follow with EFetch at `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/efetch.fcgi?db=pubmed&query_key=...&WebEnv=...&retmode=xml`. Use ESummary only when its compact summary is sufficient. For a persistent broad corpus, use the [2026 annual XML baseline directory](https://ftp.ncbi.nlm.nih.gov/pubmed/baseline/) and [daily update directory](https://ftp.ncbi.nlm.nih.gov/pubmed/updatefiles/) (the linked directories include README/checksum manifests; exact files change over time) from the official FTP distribution. NLM says baseline is a complete snapshot, and daily files carry new, revised, and deleted citations. Apply updates as upserts/tombstones and reload the annual baseline when released. ESearch supports modification-date (`mdat`) and Entrez-date (`edat`) filters, plus History server paging. PubMed ESearch can return only the first 10,000 matching records for one query; EDirect can batch larger PubMed sets, or partition by date ranges/other stable query slices into <10,000-record sets and deduplicate. Do not assume `retstart`/History removes that PubMed ceiling. A saved query is not a substitute for replaying update records. Runnable small probe: `curl -sG 'https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi' --data-urlencode 'db=pubmed' --data-urlencode 'term=Gaucher disease[Title/Abstract]' --data-urlencode 'retmax=1' --data-urlencode 'retmode=json' --data-urlencode 'tool=rare_disease_kg' --data-urlencode 'email=YOUR_EMAIL'`; then use returned PMID with `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/efetch.fcgi?db=pubmed&id=PMID&retmode=xml`. A live probe returned HTTP 200, count 6,008, one ID, and EFetch returned PubmedArticle XML (see probe JSON). NCBI recommends API key when exceeding 3 req/s, and requests must include tool/email (see in-depth documentation).

**Scope and rights:** PubMed is citations/abstracts, not full-text hosting; it includes MEDLINE and citations from other NLM literature resources. Abstracts may be present, missing, structured, or corrected. Access to a PubMed citation does not grant republication rights for its abstract or linked article. Follow the baseline/update README terms, NCBI terms, and rights of publishers/authors; don’t treat public API availability as a blanket license. Full text should be fetched only from an explicitly licensed provider such as eligible PMC articles.

**Fields and KG links (proposed):** PMID as the stable source key; DOI(s), PMCID where present, title, abstract sections, author name/affiliation, journal/ISSN, publication types, MeSH headings/qualifiers, keywords, dates, grant identifiers, correction/retraction notices, language, and publication status. Model `Article —MENTIONS→ Disease/Phenotype/Gene/Drug` only as an extracted, confidence-scored assertion with supporting text span and PMID; `Article —HAS_AUTHOR→ Author` with conservative identity resolution; `Article —HAS_MESH→ MeSH concept`; `Article —HAS_DOI→ DOI`; `Article —CITES/RELATED_TO→ Article` only where an explicit link is sourced. Record source publication date separately from record creation/revision dates.

**Quality pitfalls:** Search terms miss diseases with synonyms, legacy names, phenotype-first abstracts, or recently coined nomenclature; broad disease queries yield false positives. MeSH indexing is delayed/absent for new and non-MEDLINE records. Abstracts are not full text, are author-supplied, can omit methods/results, and may change across citation revisions. PubMed has corrections/retractions and duplicate versions; use linked notice records and publication types. Author names are ambiguous; grant and affiliation strings need normalization. Do not interpret textual co-occurrence as a confirmed biological relation.

**Feasibility:** High for metadata and abstracts at broad scale through baseline + updates; moderate for precise disease filtering; low for unrestricted full text. XML is verbose but structured and carries record history/identifiers. Maintain a source snapshot date and update-file watermark.

## S05 — PubMed Central (PMC)

PDF pages: 3, 5. **Acquisition summary:** OAI-PMH/current PMC Cloud; article-level reuse rights

**Metadata route (doc-only):** The current [PMC OAI-PMH API](https://pmc.ncbi.nlm.nih.gov/tools/oai/) is `https://pmc.ncbi.nlm.nih.gov/api/oai/v1/mh/`; it serves metadata for all PMC items in `pmc_fm`/`oai_dc`. Use `ListIdentifiers`/`ListRecords` with `from`/`until` and resumption tokens. The source documentation limits `ListIdentifiers` pages to 50 and `ListRecords` to 10. PMC IDs are PMCID, represented to OAI-PMH as `oai:pubmedcentral.nih.gov:<numeric-pmcid>`. `set=pmc-open` selects content eligible for full-text retrieval. The [PMC Copyright Notice](https://pmc.ncbi.nlm.nih.gov/about/copyright/) says systematic article downloads from the main site are prohibited; use only OAI-PMH, E-utilities, PMC Cloud or official distribution service for automated retrieval. NCBI announced that the updated PMC Cloud would become the primary dataset file route in August 2026 and FTP files would be removed in that month ([transition notice](https://ncbiinsights.ncbi.nlm.nih.gov/2026/02/12/pmc-article-dataset-distribution-services/)). This is no longer only a future schedule: as of the 2026-10-03 research date, PMC’s [OA Web Service notice](https://pmc.ncbi.nlm.nih.gov/tools/oa-service/) says the service is no longer available (dated August 25, 2026), and the current OAI-PMH documentation lists PMC Cloud as an approved automated retrieval service. Use the current [PMC Cloud Service](https://pmc.ncbi.nlm.nih.gov/tools/pmcaws/) and verify the linked README before building paths. The OAI-PMH route remains separately documented and live in source docs. Do not build new ingestion around the retired OA Web Service or assume old FTP package paths persist.

**Full-text route and permissions (doc-only):** For licensed JATS full text, use OAI-PMH `ListRecords`/`GetRecord` with `metadataPrefix=pmc`, scoped to `set=pmc-open`, or NCBI E-utilities PMC EFetch for authorized records; for dataset bulk file retrieval follow the currently documented [PMC Cloud Service](https://pmc.ncbi.nlm.nih.gov/tools/pmcaws/) rather than scraping pages. OAI-PMH metadata is broader than the full-text set: not all articles permit text mining/reuse. Check item-level machine-readable license/rights before storing or redistributing full text. The OA subset itself has different commercial/noncommercial/other license buckets; “free to read” is not equivalent to commercial text-mining or redistribution permission. PMC Author Manuscript content also has source-specific terms and should not be silently conflated with CC-licensed publisher articles. Throttle OAI-PMH to at most 3 requests/second, sequentially; documentation advises off-peak for >100 calls.

**Fields and KG links (proposed):** PMCID as primary key, with PMID/DOI crosswalk; article title/abstract/body sections, paragraph/table/figure captions and references when licensed, author/affiliation, journal, publication/version dates, license URI and license text, funding, acknowledgments, correction/retraction relationships. Reuse PubMed’s Article node by DOI/PMID/PMCID crosswalk but keep separate source assertions and version/accession records. Candidate KG edges are `Article —MENTIONS→ entity` grounded in section+offset+quoted evidence, `Article —HAS_LICENSE→ License`, `Article —HAS_VERSION→ ArticleVersion`, and reference edges.

**Quality pitfalls:** Licensing can vary at article and even component level (figures/third-party materials); preserve notices and source URLs. JATS structure and tagging quality differ by publisher and historical content. PMC author manuscript and published version can duplicate the same work but differ substantially. Entity extraction from full text can increase recall while increasing negation/speculation errors; distinguish introduction speculation, methods, results, and discussion. Article corrections/retractions and version history must flow into assertions. PMC/PMID/DOI links are incomplete in some records.

**Feasibility:** High for metadata; medium for full text limited by license, dataset logistics, and XML heterogeneity. Licensed Open Access subsets support a substantial, auditable text-mining corpus. Store license eligibility per document before deriving text-based facts.

## S06 — ClinicalTrials.gov

PDF pages: 4, 5. **Acquisition summary:** API v2; search and update filter samples verified

**Official URLs:** [API overview](https://clinicaltrials.gov/data-api/about-api), [API v2 OpenAPI](https://clinicaltrials.gov/api/gui), [study data structure](https://clinicaltrials.gov/data-api/about-api/study-data-structure), [download studies](https://clinicaltrials.gov/data-api/about-api/download-studies), [CSV fields](https://clinicaltrials.gov/data-about-studies/csv-download).

**Route:** Current API v2 is `https://clinicaltrials.gov/api/v2/studies`; a single record is `https://clinicaltrials.gov/api/v2/studies/{NCTId}`. Search accepts condition/other query fields and returns paged studies with `nextPageToken`; continue until exhausted. Use `format=json` (default) or documented CSV/JSON outputs and `pageSize` to manage response size. For full local replication, use the official [study-data download page](https://clinicaltrials.gov/data-api/about-api/download-studies) and API. I did not confirm a separate daily update feed or a stable bulk-delta manifest; do not design around one until the current download docs confirm it. The API supports incremental candidate retrieval via documented advanced filters such as `AREA[LastUpdatePostDate]RANGE[2025-01-01,2025-01-31]`, followed by complete paging and periodic reconciliation/full sync. Preserve downloaded record versions and account for the source warning that submitted and posted update dates may differ. **Live tested:** opened `https://clinicaltrials.gov/api/v2/studies/NCT04280705`; it returned JSON with NCTId, sponsor, status, dates, condition, design, arms, interventions and outcomes. A live one-result search returned HTTP 200 with `studies` and `nextPageToken`; a live advanced `LastUpdatePostDate` interval filter also returned HTTP 200 and a page token. The download-doc page could not be parsed in the browser research tool, so bulk cadence remains unverified.

**Scope and rights:** Public registry records cover interventional and observational studies, including results modules when submitted; registration completeness and results availability vary. Registry text fields are largely sponsor/investigator submissions; they are not peer-reviewed findings. Respect [ClinicalTrials.gov terms](https://clinicaltrials.gov/about-site/terms-conditions) and copyright notices. Public record access does not give blanket rights to third-party linked documents or submitted attachments.

Runnable one-result probe: `curl -s 'https://clinicaltrials.gov/api/v2/studies?query.cond=Gaucher%20Disease&pageSize=1'`; save and pass `nextPageToken` on the next request. **Fields and KG links (proposed):** NCTId as stable trial key; secondary IDs, brief/official titles, status, conditions, keywords, sponsor/collaborators, interventions, arm groups, eligibility, design, phase, enrollment, locations, outcomes, results, dates, references, and record history. Map submitted conditions to normalized disease IDs with evidence; `Trial —STUDIES→ Disease`, `Trial —TESTS→ Intervention`, `Trial —HAS_ARM→ Arm`, `Trial —HAS_OUTCOME→ Outcome`, `Trial —SPONSORED_BY→ Organization`, `Trial —HAS_PUBLICATION→ Article` where explicit references/PMIDs/DOIs are given. Retain source condition strings and normalized mapping confidence.

**Quality pitfalls:** Condition fields are not a controlled rare-disease ontology; synonyms and spelling vary. “Rare” cannot be inferred reliably from a label alone or US prevalence thresholds without jurisdictional context. Trials may use umbrella indications; sponsor-entered records can be incomplete, stale, or changed after posting. Trial statuses and dates need event-time handling. Multiple NCT records can be a multi-arm/platform program or separate protocol; don't merge by title alone. Registered outcomes are planned measures, not results. Be precise about actual vs estimated dates and enrollment.

**Feasibility:** High. API and bulk records are well structured, stable NCT IDs support joins, and updates are frequent. Moderate curation is required for disease normalization, sponsor identity, intervention ingredients, and multi-protocol trials.

## S07 — NIH RePORTER

PDF pages: 4, 5. **Acquisition summary:** POST API or ExPORTER files; project sample verified

One read-only check of Genetic Alliance UK's robots file returned 200 `text/plain`, with `User-agent: *`, disallowing `/wp-admin/` and allowing `/wp-admin/admin-ajax.php`; it exposes a sitemap. Its [citations policy](https://geneticalliance.org.uk/citations-policy/) permits non-commercial reproduction of original, unmodified website material with attribution, but says nothing explicit about bulk extraction or converted KG data. Use a small attributed seed within that permission, and obtain clarification for recurring/bulk transformed reuse. No API/export was confirmed. Directory membership indicates alliance membership, not exhaustive UK patient-organization coverage and not necessarily a disease relation.

## S15 — MONDO

PDF pages: 5. **Acquisition summary:** Pinned ontology releases; release/header sample verified

**Identity and official entry points.** MONDO is a harmonized disease ontology maintained by the Monarch Initiative ([Mondo site/downloads](https://mondo.monarchinitiative.org/pages/download/); [source repository](https://github.com/monarch-initiative/mondo)).

**What to extract and KG shape (proposed).** Extract MONDO IDs, preferred labels, synonyms, definitions, obsolete/replaced-by metadata, ontology hierarchy, and cross-ontology equivalence/mapping axioms. Model `Disease --subclass_of--> Disease` and `MONDO disease --equivalent_to / xref--> source disease identifier` while preserving axiom type, source, and evidence. Use `MONDO:nnnnnnn`/`http://purl.obolibrary.org/obo/MONDO_nnnnnnn` as canonical ID forms.

**Bulk/API routes and sample (live-probed, small range).** The latest official release at check time was `v2026-09-01` ([release assets](https://github.com/monarch-initiative/mondo/releases/tag/v2026-09-01)). It includes complete `mondo.owl` (254.2 MB), `mondo.obo` (53.1 MB), `mondo.json` (107.6 MB), and `mondo-rare.owl` (160.4 MB). Exact pinned examples: [mondo.owl](https://github.com/monarch-initiative/mondo/releases/download/v2026-09-01/mondo.owl), [mondo.obo](https://github.com/monarch-initiative/mondo/releases/download/v2026-09-01/mondo.obo). I sent a `Range: bytes=0-2047` request to the pinned OBO asset; HTTP 206 returned only 2,048 of 53,134,854 bytes and confirmed OBO format plus `data-version: releases/2026-09-01`. The complete OWL edition carries inter-ontology equivalence axioms; OBO omits them. No general-purpose query API is needed for full ontology import. Stable PURLs `http://purl.obolibrary.org/obo/mondo.owl`, `.obo`, and `.json` are useful moving targets; pin GitHub releases for reproducible builds. The release workflow docs describe monthly releases with ad hoc additions.

**Reuse, updates and pagination.** Mondo files are offered under CC BY 4.0 ([download page](https://mondo.monarchinitiative.org/pages/download/)). Attribute, retain license notice, and indicate changes as required by CC BY. Ontology files are public; no pagination applies. Preserve release/version IRI and checksum if reproducible KG snapshots matter.

**Pitfalls and feasibility.** High feasibility and a good disease normalization spine. The complete OWL edition carries explicit equivalence axioms, while OBO omits those axioms; choosing OBO alone loses equivalence semantics. Xrefs are not uniformly strict equivalence: inspect relation/axiom annotations and provenance rather than converting every xref into `owl:sameAs`. MONDO IDs can be deprecated or merged; retain replacement history. `mondo-rare.owl` is a subset product and should not be mistaken for all MONDO diseases.

## S16 — Press releases

PDF pages: 5. **Acquisition summary:** Issuer archives/feeds; preserve announcements and corroboration

**Identity and evidence.** Another source class. Prefer the original issuer's newsroom, then use syndicated copies only for discovery. For example, the [STXBP1 Foundation's STARR announcement](https://www.stxbp1disorders.org/news/4mvj7pxvmx77rbs1cd1jv01fwdvo52) announces a study; the [current STARR page](https://www.stxbp1disorders.org/starr) is a separate source for follow-up. An announcement is evidence that the issuer announced something, not that the program remains active or achieved a scientific result.

**Extraction procedure (proposed).** Seed issuer news archives from approved organization/company/university domains. Discover RSS/Atom if actually linked; otherwise follow archive pagination and individual canonical article links. For permitted automation, parse `NewsArticle` JSON-LD and visible title, issuer, date, body and outbound study/paper links. Save source URL and a hash; deduplicate syndicated releases by original URL, title/date and normalized content fingerprint. Identify entities and event types with a schema-constrained extractor, retaining text evidence and distinguishing future plans, completed milestones and claims of efficacy. Attach original release and any later correction to the same event without deleting history.

**Record design.** Local event ID plus canonical release URL; announced-at date, retrieved-at time, issuer, organization/researcher names, disease/gene mentions, asset/program names, funder, amount/currency if stated, target dates and evidence spans. Proposed edges: `Issuer ANNOUNCED Event`, `Event CONCERNS Asset/Project`, `Event MENTIONS Disease`, and `Event CORROBORATED_BY Trial/Publication` only after identity verification. Do not make `Drug TREATS Disease` from a press release.

**Rights, updates and completeness.** Read source terms; a press release is not automatically public domain. Keep metadata, links and only permitted evidence excerpts; don't mirror entire news sites. Refresh enabled feeds/archives weekly and recheck linked study/program status monthly. Page-number pagination is source-specific; record visited pages and failures. The same release on five websites is one underlying piece of evidence, not five independent confirmations. Negative findings (no trial/publication located) should retain the queries and date. No universal API or cross-publisher license was verified.

**Feasibility.** Useful secondary discovery signal, lower confidence than primary registries and research. The example announcement and follow-up were read; no general crawler was built. An initial extraction should show an announcement node and a distinct current-status assertion, rather than silently equating the two.

## S17 — Jackson Laboratory

PDF pages: 5. **Acquisition summary:** MGI reports/batch export; samples verified; asset availability separate

**Identity and route choice.** JAX is an institution with several datasets, not a single download. [JAX's tools directory](https://www.jax.org/research-and-faculty/data-science/tools-and-databases) identifies Mouse Genome Informatics (MGI), MouseMine and the International Mouse Strain Resource (IMSR). Use MGI for biological annotations, then repository/catalogue links for actual resource availability. MouseMine offers an API; bulk MGI reports are a simpler starting point for reproducible ingestion.

**Concrete extraction.** Follow the [MGI report index](https://www.informatics.jax.org/downloads/reports/index.html) to tab-delimited reports: `HOM_AllOrganism.rpt` (orthology), `HMD_HumanPhenotype.rpt` (human/mouse gene and high-level mouse phenotype links), `MGI_PhenotypicAllele.rpt` (alleles and literature), and `MGI_Strain.rpt` (strain identity). The index gives field order and links. Parse without assuming headers; use a format-specific schema and preserve MGI IDs. For a seed, use [MGI Batch Query](https://www.informatics.jax.org/batch) to export selected genes and supported annotations. Follow its explicitly linked disease-model/allele records before claiming a strain models a human disease. Report samples were probed; see the log for status and sampled column counts. A sampled report does not validate all row variants or join cardinalities.

**Mapping (proposed).** `HumanGene ORTHOLOG_OF MouseGene`, `MouseAllele IN_GENE MouseGene`, `Model HAS_ALLELE MouseAllele`, `Model HAS_MOUSE_PHENOTYPE MP`, and evidence-qualified `Model MODELS Disease`. Keep species, genotype, zygosity, strain background, sex/age when available, publication reference, genome assembly and source version. Mouse phenotypes use `MP:` rather than `HP:`; any cross-species phenotype mapping is a separate assertion. MGI allele IDs, MGI strain IDs, IMSR records and JAX stock numbers are not interchangeable. Store local asset IDs linked to each native record.

**Access, maintenance and limitations.** [MGI licensing](https://www.informatics.jax.org/mgihome/other/copyright.shtml) gives CC BY 4.0 for data/annotations and separate restrictions for images. Attribute MGI and pin downloaded reports by date/hash. Proposed refresh is weekly snapshot comparison; no incremental deletion feed is established here. Buying/accessing a mouse line is governed by the relevant repository and material-transfer conditions, separate from annotation reuse. Recheck live catalogue availability before presenting an asset as obtainable. Orthology or shared phenotype alone does not prove a suitable disease model. Core MGI annotation extraction is feasible; catalogue/stock availability ingestion needs provider-specific validation.

## S19 — bioRxiv

PDF pages: 5. **Acquisition summary:** Date/cursor API; metadata sample verified; per-version rights

**Official URLs:** [bioRxiv API](https://api.biorxiv.org/), [API endpoint help](https://api.biorxiv.org/details/biorxiv/help), [bioRxiv policies](https://www.biorxiv.org/about-biorxiv).

**Route (doc-only):** `https://api.biorxiv.org/details/biorxiv/{start-date}/{end-date}/{cursor}/json` returns metadata in a date interval, 30 records per page; advance cursor by page size and use the `messages` array counts to detect exhaustion. API accepts subject `category`; single-item lookup is `/details/biorxiv/{DOI}/na/json`. Fields documented: DOI, title, authors/corresponding author and institution, date, version, type, license, category, JATS XML path, abstract, published status, server. The API has no stated durable change-token contract: poll overlapping date windows and upsert by DOI+version, because revised versions retain DOI and `version` changes. Runnable probe: `curl -s 'https://api.biorxiv.org/details/biorxiv/2025-01-01/2025-01-01/0/json'` (replace `biorxiv` with `medrxiv` for that server). Live one-day date-interval calls returned HTTP 200: bioRxiv returned 30 records in the first page and medRxiv 15; both returned `messages` and `collection` with the documented metadata fields (see probe JSON).

**Scope and rights:** Research manuscripts before peer review; API metadata includes abstract, version, license and a JATS path. Do not presume that an API-provided JATS location authorizes unrestricted text reuse. Respect each record’s license and the server’s [text/data mining terms](https://www.biorxiv.org/tdm), and separately confirm bulk retrieval mechanics/rates before production. Preserve clear “preprint/not peer-reviewed” status. When a peer-reviewed publication exists, link it as a distinct work/version through explicit DOI/metadata; do not silently replace the preprint.

**Fields and KG links (proposed):** DOI as work family identifier plus explicit version node; authors/corresponding institution, category, abstract, posting date, license, JATS path, published flag, and related journal DOI when verified. Edges: `PreprintVersion —VERSION_OF→ PreprintWork`, `PreprintWork —PUBLISHED_AS→ Article` only with verified DOI crosswalk, `PreprintVersion —MENTIONS→ entity` with version-specific evidence.

**Quality pitfalls:** Not peer reviewed; extraction can mistake hypotheses and proposed mechanisms for established findings. Version changes may alter claims, authors, and text. BioRxiv’s categories are not disease ontology labels. Journal publication can be substantially revised, retracted, or have a different author list/title. Maintain version-specific text and lifecycle status, and ingest retraction/correction status from authoritative publication metadata where available.

**Feasibility:** High for metadata; moderate for licensed full-text mining and version reconciliation. API is convenient and expressly paginated; do not assume a universal commercial reuse license.

## S20 — medRxiv

PDF pages: 5. **Acquisition summary:** Date/cursor API; metadata sample verified; per-version rights

**Official URLs:** [medRxiv API](https://api.biorxiv.org/), [API endpoint help](https://api.biorxiv.org/details/medrxiv/help), [machine access/TDM](https://www.medrxiv.org/tdm), [FAQ/licensing](https://www.medrxiv.org/about/FAQ).

**Route (doc-only):** Same API pattern, with server `medrxiv`: `https://api.biorxiv.org/details/medrxiv/{start-date}/{end-date}/{cursor}/json`; 30 records/page, cursor continuation, optional category, and DOI detail route `/details/medrxiv/{DOI}/na/json`. API returns DOI, title, authors, dates, version, type, license, category, JATS XML path, abstract, published status and server. Poll overlapping windows for new/revised records; upsert by DOI and version. For existing DOI, record all versions or explicitly document a most-recent-version policy; API does not itself provide a documented full change log.

**Scope and rights:** Health and medical preprints; all are not peer reviewed. FAQ states authors retain copyright and choose from restrictive/no-reuse through CC licenses; item-level selection governs reuse. Metadata/API access is not blanket full-text redistribution permission. TDM page indicates machine access resources and ability to restrict access for license breaches. Read the license on each version before storing full text or deriving redistributable outputs. Do not make clinical recommendations from unreviewed preprints; label evidence as preliminary. Preserve published status and connect journal version separately.

**Fields and KG links (proposed):** Same work/version structure as bioRxiv; preserve medRxiv-specific category and license, version, dates, abstract and author details. Link preprint to trial or disease concepts only with evidence spans; link journal publication through explicit DOI or corroborated bibliographic crosswalk. A trial registration mentioned in the manuscript is a candidate link requiring validation against ClinicalTrials.gov, not a direct asserted relation.

**Quality pitfalls:** In addition to non-peer-reviewed claims, health-related content carries heightened risk of premature, overinterpreted clinical associations. Categories and author-entered text are not a rare-disease ontology. Preprint-to-publication mappings can be wrong when title/author changes; DOI/version and explicit publication links are crucial. Corrections, withdrawal, and journal retraction state should be tracked independently and propagated to evidence displays without deleting historical versions.

**Feasibility:** High for metadata and abstracts; medium for full text due to per-version licensing and external file retrieval. Good for fast discovery and emerging disease terminology, but claims should remain visibly provisional until corroborated.

## S21 — RARe-SOURCE

PDF pages: 2. **Acquisition summary:** Documented UI CSV exports; API/bulk contract unverified

**Identity.** The PDF introduction links [RARe-SOURCE](https://raresource.nih.gov/about-us/), an NIH integrated rare-disease resource. Its [NCATS description](https://ncats.nih.gov/research/research-activities/rare-source) explains the disease/gene/variant/literature integration role. Treat it as an enrichment/comparison source, not independent confirmation when its facts come from the same primary datasets already ingested.

**Documented extraction route.** Its [official user guide](https://raresource.nih.gov/staticfiles/documents/Transforming-Data-To-Rare-Disease-Knowledge.pdf), especially pages 5–11 and 18–19, describes disease/gene search, CSV export of aliases and identifiers, gene-associated disease exports and LiteratureAI results export. For a seed, search each disease/gene in the public interface, record filter settings, use the provided export controls, and retain the CSV with URL, capture time and hash. Those controls are documented; they were not exercised in this research. No stable public bulk API contract was verified.

**Proposed parsing/mapping.** Parse exported column names as delivered; retain external IDs rather than fabricating a RARe-SOURCE accession. Create source-record nodes scoped to resource URL plus entity identifiers. Use verified crosswalks to MONDO/HGNC/ClinVar/PMID; retain upstream provider lineage for each assertion. Literature co-occurrence should create a discovery candidate, never a proven causal mechanism. Preserve manually curated, computationally predicted and imported annotations as separate evidence types.

**Rights, updates and feasibility.** The About page requests resource citation and gives a specific citation for SLC6A8 curated variants. That is not a blanket license for all imported content. Confirm export/upstream terms and any automated-access agreement before scaling. Proposed monthly repeat exports for a fixed seed; compare identifiers and hashes and note that changed search coverage can mimic deletion. Useful for reference and gap analysis; core ingestion should use primary providers for independent provenance. The public guide and About page were reviewed; schema, data-export completeness and API availability remain implementation checks.
