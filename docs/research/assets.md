# Research assets, websites and contextual sources

Checked 2026-10-03. Provider facts cite official pages; extraction workflows and refresh schedules are proposed. A documentation check does not certify bulk access or reuse rights. Read-only sample results, when available, are in [asset-probes.json](asset-probes.json).

## Verified patient-group / patient-org websites

**Identity and evidence.** This is a source class, not one database. Start with official domains obtained from the directories in S08–S14, then confirm the organization on its own About/Contact pages. A concrete example is the [STXBP1 Foundation biorepository page](https://www.stxbp1disorders.org/biorepository), which names a partnership with COMBINEDBrain, research sample types and a public research contact. Its [STARR page](https://www.stxbp1disorders.org/starr) describes a natural-history study. These are examples of discoverable assets, not evidence that any particular researcher can immediately obtain samples or data.

**Extraction procedure (proposed).** For a first disease cluster, build an allowlist of 5–10 verified domains. Check each site's terms and robots policy; use a documented export/feed where supplied. Otherwise, curate a small set of public Research, Registry, Biobank, Studies and Resources pages. For permitted automation, follow sitemap and visible navigation links, constrain the domain and path, canonicalize URLs, extract HTML headings/main text and JSON-LD when present, and follow public PDF brochures. Parse text PDFs with `pdftotext`; apply OCR only for image-only pages and mark OCR-derived evidence. A website crawler needs site-specific parsing and a review queue; there is no universal patient-group API. Dynamic content may require reading the rendered public UI. Do not guess hidden API routes or treat a crawler's failure as evidence that an asset does not exist.

**Record design.** Store organization source URL, public name, country/remit when stated, disease scope, asset name/type, owner/operator, canonical asset page, study/registry identifier if explicitly given, availability statement and date, application/access procedure, public role contact URL, and evidence locator. Mint persistent local UUIDs for organizations/assets without native IDs and keep URLs as source aliases; avoid treating a renamed domain as a new organization. Proposed edges: `Organization OPERATES Asset`, `Asset STUDIES Disease`, `Organization PARTNERS_WITH Organization`. A biorepository, a registry, a contact list, and a natural-history study are distinct assets even when one organization hosts all four. Verify NCT/DOI IDs against their primary provider.

**Rights and updates.** No blanket open-data license applies. Public metadata linking can be curated, while automated bulk collection and redistribution of prose require source-specific review. Do not ingest patient stories, participant names, private registry records, or enrollment forms as graph data. A public registry landing page does not grant access to registry records. Proposed refresh: monthly for core pages, weekly for active-study pages, with conditional HTTP requests where supported, content hashes, publication/observation timestamps and manual review of changed availability. Preserve superseded claims; broken links yield `unreachable`, not `closed`.

**Feasibility.** High for a small reviewed seed; variable for global automated coverage. The specific Foundation pages were read through web tools; no site-wide harvest, permission negotiation or registry access was performed. Acceptance criterion: every organization–asset–disease edge has a source passage and the asset's access status is explicit (`public_metadata`, `application_required`, `unknown`).

## Press releases

**Identity and evidence.** Another source class. Prefer the original issuer's newsroom, then use syndicated copies only for discovery. For example, the [STXBP1 Foundation's STARR announcement](https://www.stxbp1disorders.org/news/4mvj7pxvmx77rbs1cd1jv01fwdvo52) announces a study; the [current STARR page](https://www.stxbp1disorders.org/starr) is a separate source for follow-up. An announcement is evidence that the issuer announced something, not that the program remains active or achieved a scientific result.

**Extraction procedure (proposed).** Seed issuer news archives from approved organization/company/university domains. Discover RSS/Atom if actually linked; otherwise follow archive pagination and individual canonical article links. For permitted automation, parse `NewsArticle` JSON-LD and visible title, issuer, date, body and outbound study/paper links. Save source URL and a hash; deduplicate syndicated releases by original URL, title/date and normalized content fingerprint. Identify entities and event types with a schema-constrained extractor, retaining text evidence and distinguishing future plans, completed milestones and claims of efficacy. Attach original release and any later correction to the same event without deleting history.

**Record design.** Local event ID plus canonical release URL; announced-at date, retrieved-at time, issuer, organization/researcher names, disease/gene mentions, asset/program names, funder, amount/currency if stated, target dates and evidence spans. Proposed edges: `Issuer ANNOUNCED Event`, `Event CONCERNS Asset/Project`, `Event MENTIONS Disease`, and `Event CORROBORATED_BY Trial/Publication` only after identity verification. Do not make `Drug TREATS Disease` from a press release.

**Rights, updates and completeness.** Read source terms; a press release is not automatically public domain. Keep metadata, links and only permitted evidence excerpts; don't mirror entire news sites. Refresh enabled feeds/archives weekly and recheck linked study/program status monthly. Page-number pagination is source-specific; record visited pages and failures. The same release on five websites is one underlying piece of evidence, not five independent confirmations. Negative findings (no trial/publication located) should retain the queries and date. No universal API or cross-publisher license was verified.

**Feasibility.** Useful secondary discovery signal, lower confidence than primary registries and research. The example announcement and follow-up were read; no general crawler was built. An initial extraction should show an announcement node and a distinct current-status assertion, rather than silently equating the two.

## Jackson Laboratory (JAX)

**Identity and route choice.** JAX is an institution with several datasets, not a single download. [JAX's tools directory](https://www.jax.org/research-and-faculty/data-science/tools-and-databases) identifies Mouse Genome Informatics (MGI), MouseMine and the International Mouse Strain Resource (IMSR). Use MGI for biological annotations, then repository/catalogue links for actual resource availability. MouseMine offers an API; bulk MGI reports are a simpler starting point for reproducible ingestion.

**Concrete extraction.** Follow the [MGI report index](https://www.informatics.jax.org/downloads/reports/index.html) to tab-delimited reports: `HOM_AllOrganism.rpt` (orthology), `HMD_HumanPhenotype.rpt` (human/mouse gene and high-level mouse phenotype links), `MGI_PhenotypicAllele.rpt` (alleles and literature), and `MGI_Strain.rpt` (strain identity). The index gives field order and links. Parse without assuming headers; use a format-specific schema and preserve MGI IDs. For a seed, use [MGI Batch Query](https://www.informatics.jax.org/batch) to export selected genes and supported annotations. Follow its explicitly linked disease-model/allele records before claiming a strain models a human disease. Report samples were probed; see the log for status and sampled column counts. A sampled report does not validate all row variants or join cardinalities.

**Mapping (proposed).** `HumanGene ORTHOLOG_OF MouseGene`, `MouseAllele IN_GENE MouseGene`, `Model HAS_ALLELE MouseAllele`, `Model HAS_MOUSE_PHENOTYPE MP`, and evidence-qualified `Model MODELS Disease`. Keep species, genotype, zygosity, strain background, sex/age when available, publication reference, genome assembly and source version. Mouse phenotypes use `MP:` rather than `HP:`; any cross-species phenotype mapping is a separate assertion. MGI allele IDs, MGI strain IDs, IMSR records and JAX stock numbers are not interchangeable. Store local asset IDs linked to each native record.

**Access, maintenance and limitations.** [MGI licensing](https://www.informatics.jax.org/mgihome/other/copyright.shtml) gives CC BY 4.0 for data/annotations and separate restrictions for images. Attribute MGI and pin downloaded reports by date/hash. Proposed refresh is weekly snapshot comparison; no incremental deletion feed is established here. Buying/accessing a mouse line is governed by the relevant repository and material-transfer conditions, separate from annotation reuse. Recheck live catalogue availability before presenting an asset as obtainable. Orthology or shared phenotype alone does not prove a suitable disease model. Core MGI annotation extraction is feasible; catalogue/stock availability ingestion needs provider-specific validation.

## RareConnect

**Current status matters.** RareConnect's [official announcement](https://www.rareconnect.org/en/announcements) states the platform retired on **5 December 2023**. Existing posts/comments remain readable, but users cannot create communities/posts or use private messaging. The PDF lists it as a stretch source without this qualification.

**Extraction plan (proposed).** Treat it as an archive for discovering historical community names and official organization links. Human-curate public community landing-page metadata: community label, canonical URL, language, represented disease as explicitly stated, linked organization and capture date. Do not build a current contact/messaging workflow around it. If a community links an external organization, validate that organization on its present official website before creating an active support lead. No documented public API or bulk export was established in this review.

**Graph representation and rights.** Use a `CommunityArchive` node keyed by canonical URL, `historical_status=read_only`, platform retirement date and evidence URL. An archive `ABOUT Disease` and an organization `SUPPORTS Disease` are different claims. Do not harvest personal health narratives, author profiles, comments or participant relationships for this public KG; they are unnecessary for the requested community/asset discovery. Public reading does not establish reuse permission. Seek platform agreement if structured archive metadata at scale is needed; no outreach was sent.

**Updates and feasibility.** Archive metadata is low priority; proposed quarterly link checks can identify external organization redirects, but never infer reactivation from an HTTP 200. Feasible for a few historical links. Unsuitable as a current source of community activity, active membership counts, available private contacts or fresh patient reports. The retirement page was checked; no archive data export was attempted.

## RARe-SOURCE

**Identity.** The PDF introduction links [RARe-SOURCE](https://raresource.nih.gov/about-us/), an NIH integrated rare-disease resource. Its [NCATS description](https://ncats.nih.gov/research/research-activities/rare-source) explains the disease/gene/variant/literature integration role. Treat it as an enrichment/comparison source, not independent confirmation when its facts come from the same primary datasets already ingested.

**Documented extraction route.** Its [official user guide](https://raresource.nih.gov/staticfiles/documents/Transforming-Data-To-Rare-Disease-Knowledge.pdf), especially pages 5–11 and 18–19, describes disease/gene search, CSV export of aliases and identifiers, gene-associated disease exports and LiteratureAI results export. For a seed, search each disease/gene in the public interface, record filter settings, use the provided export controls, and retain the CSV with URL, capture time and hash. Those controls are documented; they were not exercised in this research. No stable public bulk API contract was verified.

**Proposed parsing/mapping.** Parse exported column names as delivered; retain external IDs rather than fabricating a RARe-SOURCE accession. Create source-record nodes scoped to resource URL plus entity identifiers. Use verified crosswalks to MONDO/HGNC/ClinVar/PMID; retain upstream provider lineage for each assertion. Literature co-occurrence should create a discovery candidate, never a proven causal mechanism. Preserve manually curated, computationally predicted and imported annotations as separate evidence types.

**Rights, updates and feasibility.** The About page requests resource citation and gives a specific citation for SLC6A8 curated variants. That is not a blanket license for all imported content. Confirm export/upstream terms and any automated-access agreement before scaling. Proposed monthly repeat exports for a fixed seed; compare identifiers and hashes and note that changed search coverage can mimic deletion. Useful for reference and gap analysis; core ingestion should use primary providers for independent provenance. The public guide and About page were reviewed; schema, data-export completeness and API availability remain implementation checks.
